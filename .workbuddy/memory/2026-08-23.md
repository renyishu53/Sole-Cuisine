2. **调整工作流 `PlanRevisionWorkflow`**：LangGraph StateGraph 条件路由（revision_intent 分类 → 5 分支 meal/shopping/budget/constraint/compound → affected_agents → dependency_sync）。图内无 LLM、无 agent；自然语言→ReviseOperation 的 LLM 解析在 `plan_revise.py` 的 PlanReviseService。

## 补充：checkpoint Redis 现状更正（用户提问触发核实）
- **Redis 持久化检查点已实现且就绪**，非"应换未换"：`app/services/checkpoints.py` `CheckpointRuntime.get()` 在 `CHECKPOINT_BACKEND=redis` 时走 `RedisSaver.from_conn_string`（带 TTL，连接失败非生产环境自动回退 InMemorySaver，生产环境主动 raise）。
- **依赖已声明**：`langgraph-checkpoint-redis>=0.1,<3.0` 在 `pyproject.toml` 第 39 行（`ai` extra），无需 `uv add`。
- **默认仍内存**：`config.py:75 checkpoint_backend="memory"`；`.env` 与 `docker-compose.yml` 均未设 `CHECKPOINT_BACKEND=redis` → 实际运行仍是 InMemorySaver。
- **启用三步**：`.env` 加 `CHECKPOINT_BACKEND=redis` + 确保 ai extra 装入 venv（`uv sync --no-install-project --extra ai --extra dev`）+ 重启；docker-compose 已含 `redis:7-alpine` 且 `REDIS_URL=redis://redis:6379/0`。
- **venv 装包铁律**：禁止裸 `uv sync`/`uv add`/`uv run`（build `solochef-api` 触发 sandbox SAFE_DELETE_FAIL_CLOSED）；用 `uv sync --no-install-project --extra ai --extra dev` 或 `uv pip install`。
- 上一轮项目介绍称"checkpoint 用 InMemorySaver（生产应换 Redis Saver）"已过时——准确说法应为"Redis 已支持，默认关闭待配置启用"。

## 最终决策：工作流短期记忆维持内存化（用户拍板）
- 经过多轮讨论（Redis 已就绪/PG 适配/是否持久化/RAG 统一栈），用户最终决定**沿用 InMemorySaver，不启用 Redis 持久化、不引入 PostgreSQL**。
- 决策理由：单进程部署 + 产物已落 MySQL 为事实源 + 不想为 checkpoint 增加存储复杂度；Redis 后端代码与 `CHECKPOINT_BACKEND` 开关保留作为演进路径（"配置化降级"话术）。
- 简历话术标定点：「按单进程设计为进程内 checkpoint；持久化后端已实现、留配置开关，上多 worker 或要断点续传时改一个环境变量即可切换，无需改业务代码」——把取舍讲成有意识的架构决策而非缺陷。
- PG 兴趣未落地：用户三次问及 PG，但确认无 pgvector 统一意图后，选择保持现状栈（MySQL+Redis+Neo4j+Chroma），未采纳 PG。

## 检索架构决策：BM25 当前不必要（用户提问触发核实）
- **全项目无 BM25/sparse/hybrid 实现**（grep bm25/jieba/rank_bm25/elasticsearch/whoosh/tfidf/sparse/hybrid 全无）。
- 当前检索双路：向量路 `retrieve_vector`（dense + 可选 bge-reranker 重排）+ 图谱路 `retrieve_graph`（query_rewriter 简单中文分词 → QuerySpec → graph_store.py:337 `WHERE s.name CONTAINS $keyword` 子串匹配）。
- **图谱路的 CONTAINS 已部分承担"关键词/术语"检索**，所以精确术语命中并非完全缺失（只是朴素子串匹配，非词频排序）。
- 结论：BM25 **当前非必需**。理由：①图谱路 CONTAINS 已覆盖部分术语命中 ②语料规模小、BM25 边际收益有限 ③引入需 jieba 分词+倒排索引，新增存储运维面，违背"最小底座"原则 ④三路(dense+图谱+LLM兜底) demo 负载够用。
- 触发条件（该引入时）：知识库文档大量增长、用户频繁"点名式"查询、想做 hybrid vs dense 召回量化对比（简历亮点）。
- 若引入最契合做法：A) 升级图谱路 CONTAINS→真正 BM25（不新增底座）；B) dense+BM25 hybrid 融合（RRF/加权后再送 reranker，RAG 主流叙事）。避免新增独立 BM25 微服务。
- 简历话术："评估过引入 BM25 做 sparse-dense hybrid，但当前语料规模+图谱关键词匹配已覆盖术语命中，列为可选演进项而非必需"。
